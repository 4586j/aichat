# AI 回复表情包：调研与实现方案

> 实现更新（2026-10-25）：本地图库、聊天媒体附件、音乐服务适配和全局播放器已实现并通过模拟服务自动化验证；当前配置及接口说明见 [README](../README.md#表情包与音乐配置)。以下保留调研时的结论与设计依据。

调研日期：2026-10-24。需求：AI 根据回复语境选择并发送图片表情包，采用用户已选定的“本地优先，不足时联网搜索”。本文是实现前调研，尚未接入在线服务或修改聊天业务。

后续新增的歌曲推荐与背景音乐需求见[音乐调研与实现方案](./music-research.md)。两类聊天内容建议共用消息附件结构；背景播放器独立于聊天页面生命周期。

## 结论

建议把“选择合适的表情”和“获得可用的图片”分开：本地图库是主要来源，模型只从本轮提供的候选 ID 中选图；没有合适的本地素材时，才通过可替换的在线图源检索。联网无结果、超时或未配置时，文字回复仍正常完成。

第一版采用分类、场景描述与轻量检索，不需要立即引入向量数据库、视觉模型或另一个 Python 服务。小图库可以让当前聊天模型在同一次回复中完成选图；图库增大后，再考虑语义检索。此处是结合现有项目作出的实现建议。

## 可借鉴的选图机制

AstrBot 的原生分类模式让回复模型输出分类标签，再由程序取图；其语义模式则先检索图片描述，从候选中选择具体图片。其开发说明还把标签解析、候选校验和图片发送分开，并说明解析时需要考虑代码、链接、注释和推理区域。

对本项目，建议使用更精确的图片 ID，而非每次从一个宽泛分类中随机选图。每张图片保存简短描述，例如“猫咪竖起大拇指，适用于赞同或鼓励”，避免模型仅凭“开心”标签选到不合语境的图。选图标记只在普通回复末尾识别，代码块和引用中的示例不触发发图。

来源：[AstrBot README 的选图模式](https://github.com/anka-afk/astrbot_plugin_meme_manager/blob/main/README.md)、[解析与发送的开发说明](https://github.com/anka-afk/astrbot_plugin_meme_manager/blob/main/DEVELOPMENT.md)。

## 现有代码需要改动的位置

- `lib/model.mjs`：当前只读取模型的文本回复；通用聊天兼容接口可以继续保留，通过应用约定的选图标记表达图片选择，无须强制模型支持工具调用。
- `lib/service.mjs`：在聊天上下文中加入有限数量的候选描述；校验模型选中的 ID；把表情包作为附件，与文字分别返回。在线检索失败应只影响附件。
- `lib/store.mjs`：当前消息只有文字、知识来源和召回记忆。需要增加图库元数据和消息附件存储，并迁移已有 SQLite 数据，保留旧聊天记录。
- `public/app.js`：当前用转义后的纯文本渲染回复，不会解析 Markdown 图片。应增加专门的表情包卡片，而不是放开任意 HTML 或图片外链。
- `server.mjs`：当前图片策略为 `img-src 'self' data:`，外部图片默认无法展示。应按最终图源增加准确的媒体域名，保留其他限制；本地文件由受控资源路由提供。
- `public/styles.css`：限制图片宽高、为加载失败保留替代文本，延续现有移动端和减少动态效果设置。

## 建议的用户体验

1. 在设置中提供表情包总开关和“允许联网补充”开关；在线源未配置时明确显示状态，本地功能仍能使用。
2. 管理页支持上传 PNG、JPEG、WebP、GIF，填写名称、场景描述和标签；可以启用或停用单张图片。
3. AI 自行判断是否需要表情包，第一版每条回复最多一张，不要求每条都发送，并避开最近使用的重复图片。
4. 图片显示在对应 AI 回复的文字下方；历史消息恢复后仍能对应原来的附件。
5. 在线内容标明来源，按图源要求展示署名，不把联网搜索结果和本地图库混成同一个结果列表。
6. 动图在减少动态效果模式下提供静态预览或点击播放；图片加载失败时，保留正常文字和图片说明。

## 建议的处理流程

1. 根据当前消息、角色风格和启用的图库，准备少量候选，向模型提供候选 ID 与场景描述。
2. 模型生成文字，并可选择一个本轮候选；应用校验 ID 后发送本地图片。
3. 没有适合的本地素材时，模型可表达一个简短的检索意图，例如“猫咪庆祝”，不生成图片 URL。
4. 在线适配器仅收到必要的检索词，不接收整段会话、知识资料或长期记忆。按最终图源的许可方式检索、选取和展示。
5. 未配置在线源、没有结果或服务超时，则只返回文字。图片问题不导致本轮聊天失败，也不让模型假装已经发图。

如果使用尾部选图标记，必须校验它是否来自本轮候选，并处理代码示例、未知 ID、多个标记、空回复和错误格式。模型输出的任意 URL 不直接作为图片来源。

## 存储与历史记录

- 用户上传的图片建议保存在 `data/stickers/`，文件名由内容哈希生成，元数据保存在 SQLite。现有 `data/` 忽略规则可继续覆盖这些本地资料。
- 本地元数据至少包含 ID、显示名称、描述、标签、格式、尺寸、内容哈希、启用状态和来源说明。
- 消息附件与正文分开存储。模型历史和记忆总结继续使用正常文本，不将内部选图标记当作用户事实。
- 在线附件保存哪些字段、是否可以缓存 URL、恢复历史时是否需要重新查询，必须按最终图源要求确定，不能直接套用本地图片的存储方式。
- 停用图库图片与永久删除图片应区分：前者阻止再次选中，后者还需明确影响历史附件的展示。

## 上线前需要验证的情况

- 有本地匹配时不发生在线请求；没有匹配且允许联网时才调用在线来源。
- 未配置 Key、无结果、超时和限流均不破坏文字回复；错误与日志不泄露凭据。
- 上传文件检查真实类型、大小和尺寸；文件名不参与任意磁盘路径拼接。
- 模型不能选择不存在、已停用或未提供的 ID；代码块里的选图示例不触发图片发送。
- 附件在刷新、重启、切换角色后仍正确对应消息；数据库迁移不丢旧记录。
- 移动端长图、动图、图片加载失败和减少动态效果模式均可用。
- 本地选图质量与在线中文检索质量需要真实对话验证，不能由模拟 API 测试替代。

## 实施顺序

先完成本地图库、AI 选图协议、消息附件和历史恢复，使功能不依赖第三方账号即可使用；随后接入符合项目使用方式的在线适配器。联网部分需要选定图源、准备相应 Key，并确认客户端直连或自定义集成要求。仅在获得允许缓存的来源时，才考虑自动收藏到本地。

“本地优先、联网补充”作为产品方向已经确认；具体在线供应商及其集成方式尚未定案。中文素材应优先使用用户上传或来源清楚的资源，不因某个插件代码使用开源许可证，就推断其全部图片也获得同样授权。
