# 语义模式真实模型验收问题

更新时间：2026-11-01

范围：语义意图分析、媒体选择、知识引用及真实模型端到端验收。

## 当前结论

本轮已修复三个确定的代码问题：结构化回答不再混用旧的正文/媒体/状态标签指令；明确表情请求的选择规则不再被字符串替换删除；按本轮来源和候选生成 Schema，空来源只能输出空引用数组，表情选择与候选编号成对约束。状态预测也改为直接输出受约束的对象，消除对象与 JSON 字符串包装不一致导致的整条回答失败。

已确认约束作为独立数据传入最终回答，提示词明确禁止将禁忌降级为程度较低的备选。验收保留合成回答全文，区分“推荐少辣”和“微辣也不合适”，并避免把“不少辣味”误识别为少辣建议；这些启发式检查仍需要人工核对具体食材和做法。表情强度验收使用“比上一张再含蓄一点”，按实际发出附件的强度判断，最低强度时应澄清。

本轮完整复测仍未通过，默认保留 `legacy`。下方记录通过项、失败原文和局部重跑，不将单次通过或启发式检查通过当作完整验收成功；已保存的用户选择不变。

## 2026-11-01 本轮验收与剩余阻塞

### 已落地的代码修复

- `lib/semantic-prompt.mjs` 分离结构化与兼容回答格式，共享行为规则；`chatState.prompt` 支持结构化状态格式，避免正文、标签、JSON 互相冲突。
- 结构化回答保留明确表情请求的选择规则；无合适候选时说明原因，不通过自动选第一张掩盖遗漏。
- `lib/semantic-output.mjs` 按本轮来源编号、候选别名和状态证据消息 ID 构造 Schema。无来源只能输出 `[]`，无候选只能 `none/null`；状态直接使用对象，后端继续检查候选归属、引用编号、状态证据和资源上限。
- 规划输出 `intensityChange=lower/higher` 时，程序依据实际发出图片的强度检查边界；未知实际强度、达到最低/最高值或无法核实来源时澄清。请求强度上限不再冒充实际强度。
- 原生规划使用独立的工具提交指令，不再同时要求输出普通 JSON；明确只提交一次、不等待工具结果。保留 3200 tokens 和 75 秒上限，不重试分析，不从截断结果提取可执行动作。
- 增加合成原始响应捕获、每轮两次模型调用检查、饮食全文复核和真实强度比较用例。生产诊断仍不记录私人聊天、完整提示词或密钥。

### 原生输出预算：已定位触发形式，尚未根治

捕获到真实响应在工具参数中反复拼接完整计划、`</plan>`、`<parameter ...>` 或模型内部协议标记，`finish_reason=length`，输出 3200 tokens、推理计数为 0。这次不是“内部推理吃光预算”的旧故障，也不是未到上限就超时。原始合成响应见 `semantic-native-object-wire-trace.txt` 与 `semantic-intent-native-final-trace.txt`。这些属于对象方案的实验记录；实验在完整样例中仍失败，已撤回，未把放宽解析或增加预算作为修复。

最终保留的受限字符串计划加独立证据方案，已拆分原生提交指令。六个问题样例曾全部通过，但完整 57 条仍有两条失败：一次“换回上一版”超时，以及一次工具参数无效。其中“能再换一张吗？”把 `</plan><musicEvidence>...` 混入计划字符串。后端拒绝该参数，未执行媒体。严格 Schema 约束不能在这个服务上被当作成功保证，也不能因单次恢复就默认启用语义模式。

### 饮食约束：检索已正确，最终措辞仍需修复

已确认的“不吃辣”始终召回，并作为独立约束传入回答。部分复测已能正确给出完全不辣的选项、点单说明及替代调味；警示语中的“微辣”不能直接当成违规推荐。验收启发式规则仅作初筛，`requiresContentReview=true` 的回答必须继续审查。

本轮较早的原生复测出现过“辣味很少或不辣”。最新原生完整端到端仍推荐“少量白胡椒”，另一条不辣替代做法最后变成“不太辣”。后者自动检查曾判通过，人工复核不予放行：不能把完全禁止的约束变成减量，也不能只看开头承认约束。证据见 `semantic-chat-native-transport-final.json` 的 `memory` 和 `memory_alternative`。仍需改进约束落实与内容验收，不能宣称已全部解决。

### 服务故障与验收门槛

最终原生端到端在表情序列、住院场景和换歌序列首轮遇到模型服务错误，关联后续步骤无法完成；这些没有被当作成功。标签最新真实浏览器同样在分析阶段遭遇服务错误。应用没有自动收费重试、猜测媒体动作或提交迟到附件。恢复服务后应重跑完整矩阵，不能仅拼接局部成功记录来改变默认值。

## 1. 连续换表情时偶发遗漏附件

**复现路径**

1. 使用语义模式和真实模型，准备可检索的表情图库。
2. 依次发送“发一张开心的表情”“再来一张”“换个含蓄的”。
3. 检查每轮是否展示不同的、符合意图和强度要求的表情。

**已观察到的结果**

- 最新完整端到端报告的第二轮失败：意图分析为 `again`，置信度为 `high`，远程检索得到 2 个候选，但最终没有新的表情附件。
- 此前一次调试捕获到模型选中了有效候选，却将 `<qiyi-media>` 标记紧接正文输出。当前解析器要求标记独占一行，因而没有执行该标记。
- 上述格式问题是已确认的一种失败原因；最新第二轮失败没有保存最终回答原文，**不能断言两次失败原因完全相同**。
- 提示中增加换行要求后，三轮局部复测曾全部通过，但后续完整复测仍发生遗漏。

**约束与处理方向**

- 应改进最终回答中表情选择的可靠性，并捕获合成测试的失败输出以定位剩余原因。可评估结构化选择等方式，方案需兼容流式输出及现有模型协议。
- 不得直接将代码块、引用、HTML 注释或普通正文中的示例标记当作媒体操作。只允许选择本轮经过筛选的有效候选；模型明确认为没有合适候选时，不应静默附图。
- 表情判断依赖图库的文字元数据；没有视觉能力的模型不能声称看见图片，也不能编造元数据未描述的内容。测试图库应保证描述、情绪和强度一致，且确有可选候选。

## 2. 知识追问偶发缺少来源引用

**复现路径**

1. 使用隔离测试文档，询问“新人报到要办哪些手续”。
2. 在同一会话继续问“那之后怎么办”。
3. 检查是否召回对应文档，并核对回答使用文档事实时是否在相关句子旁标注本轮有效来源编号。

**已观察到的结果**

- 最新完整端到端报告中，追问召回 1 条来源，但回答未出现相应来源编号。
- 加强追问引用提示后，单独复测曾通过，随后完整复测再次遗漏。
- 最新失败报告只记录了引用检查结果，没有保存该次回答原文，不能仅凭报告断定模型具体引用了哪些事实。追问也可能指向文档未覆盖的后续事项，复现时应结合回答内容判断：明确说明资料不足或给出标明性质的一般建议，与使用资料事实却不标注来源应分开评估。
- 当前引用校验只能检查编号是否属于本轮来源，不能证明被引用的资料支持对应论点。曾出现一般性建议与来源编号位置容易混淆的情况。

**处理方向**

- 提高多轮回答的引用可靠性；对资料不足的情况如实说明，不通过自动补编号伪造依据。
- 在合成场景中记录失败回答并人工核对：事实、步骤和编号是否对应；对未使用资料事实的回答，不应仅因缺少编号判定错误。

## 3. 输出预算和超时

早期意图分析在 1600 和 3200 输出 token 的测试中，曾将预算耗在模型内部推理上，未返回计划。原生工具参数也曾出现格式标记混入。当前对已验证的火山方舟官方地址及 `ark-code-latest`，意图分析关闭深度思考，并使用严格结构化输出或受限原生工具参数；失败时不执行媒体，也不自动重试。

最终回答曾超过 90 秒并超时。当前该模型在语义模式的最终回答也关闭深度思考，以降低延迟；这会失去对应回答的深度思考能力，不代表所有任务质量不受影响，也不能保证服务永不超时。其他服务商不接收这些专有参数。分析阶段上限为 75 秒；曾有一次并发重复测试在该限制处超时，随后串行 20 次通过，不能据此否定长尾风险。

后续验收应分别记录分析耗时、正文首字耗时、总耗时、输出预算及失败类别，并覆盖取消操作；不得记录真实用户历史、密钥或完整私有提示词。应继续检查不同模型的质量和兼容性，避免将当前模型的结果推广到其他服务。

## 4. 已修复和已验证的范围

- 原生工具规划使用受限计划及分别校验的音乐、表情证据；一项证据无效不会取消另一项有效请求。
- 修复媒体续接对同一会话内较早表情请求的引用，引用链有界；替换对象、跨会话或无法验证的引用不能沿用。
- 检索会保留用户原始问题，减少模型改写遗漏原词；近期安全上下文有界保存，并支持基于当前用户原文的状态更正。
- 当前配置模型的独立意图样例，标签与原生协议各有一次 53/53 通过；本地测试 764 项、相关浏览器回归 28 项通过。
- 两种协议的真实模型浏览器测试均曾通过音乐和表情展示、点击前不请求音频以及点击后播放检查。

以上结果是特定时间、模型与隔离测试数据的有限样本，不等于完整端到端验收通过，也不保证其他模型或表达方式无误。

## 重新验收要求

1. 修复两个未解决问题，对失败的具体原因保留可复现证据；合成测试中覆盖多轮换图、强度变化、没有合适候选、引用或代码块中的媒体标记、知识首问和追问。
2. 标签与原生两种协议分别运行真实模型的完整意图样例、端到端及浏览器验收；保留失败和重试记录，不以单项补跑成功替代完整通过。
3. 检查来源编号的有效性，并人工核实测试回答中事实和来源的对应关系；资料不足时应如实说明。
4. 验证预算耗尽、超时、取消、媒体开关和服务故障时不误执行媒体、不提交迟到附件；记录模型、协议、测试时间、耗时和局限。
5. 完整验收通过后再修改默认模式，并复测新安装默认值、已保存的兼容模式、设置界面和配置文档。

## 复测入口与证据

在项目根目录使用 PowerShell，脚本读取本地模型连接配置和密钥，只发送构造的测试内容。运行真实模型测试会产生模型请求和相应费用；报告保存在本地 `test-reports/`，不保证随仓库提交。

```powershell
# 分别运行两种协议的独立意图样例

node scripts/evaluate-semantic.mjs
$env:SEMANTIC_EVAL_MODE='native'
node scripts/evaluate-semantic.mjs

# 完整端到端场景；分别将协议设为 tags 和 native 运行

node scripts/evaluate-semantic-chat.mjs

# 浏览器验收；分别将协议设为 tags 和 native 运行
node scripts/evaluate-semantic-browser.mjs

# 本地回归
node --test --test-reporter=spec tests/*.test.mjs
npx playwright test tests/semantic-browser.spec.mjs tests/streaming-browser.spec.mjs tests/settings-browser.spec.mjs --reporter=line
```
