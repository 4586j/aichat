# 聊天歌曲推荐与背景音乐：调研和实现方案

> 实现更新（2026-10-25）：本地图库、聊天媒体附件、音乐服务适配和全局播放器已实现并通过模拟服务自动化验证；当前配置及接口说明见 [README](../README.md#表情包与音乐配置)。以下保留调研时的结论与设计依据。

调研日期：2026-10-24。本文继续[表情包调研](./sticker-research.md)，加入用户提出的“AI 在聊天中推荐歌曲”和“背景音乐”需求。当前仍处于实现前调研阶段，没有接入音乐账号或修改播放功能。

**选型更新**：用户已指定 `D:\al\erp\music` 的现有音乐平台作为音乐源，并确认服务地址先留空，后续在设置中填写。未配置时不自动连接。实际接口、鉴权、地址检查与接入链路见[现有音乐平台接入方案](./music-source-integration.md)。下方其他平台的资料保留为前期调研参考，不再作为第一版接入前提。

## 两类体验

**聊天推荐歌曲**：AI 根据用户的请求、聊天语境和明确表达的偏好推荐歌曲。回复中展示歌名、歌手、推荐理由及可靠的平台入口；具备可用播放来源时，再显示应用内播放按钮。

**背景音乐**：用户主动开启后，音乐在浏览不同页面、聊天和查看记忆时连续播放，支持暂停、音量、切歌和循环。AI 可以推荐适合的音乐或播放列表；默认不因一条普通回复突然切歌。

“推荐到一首歌”“核实这首歌的信息”和“在应用内完整播放”是三个不同能力，需要分别处理。没有音源时也能提供真实、有出处的推荐，不能将歌曲搜索结果当成可播放文件。

## 聊天中的歌曲卡片

建议的流程：

1. AI 给出候选歌名、歌手以及与当前语境有关的推荐理由，不自行编造歌曲 ID、封面地址或音频 URL。
2. 音乐适配器检索并核对候选，尤其区分原唱、翻唱、现场版和同名歌曲。
3. 能确认的结果保存来源和稳定标识，展示歌曲卡片；无法核实的候选明确标为待确认，并提供“搜索这首歌”的入口，不显示假装可播放的按钮。
4. 卡片按来源能力分别提供“打开平台”“播放本地音源”或其他获准的播放方式；不把外部平台跳转包装成应用内完整播放。
5. 只有实际有可用音源时，才提供“设为背景音乐”；外部平台的普通网页链接不能直接赋给音频播放器。

第一版建议每次最多推荐一首，需要更多时由用户继续询问。平常回复可以不推荐，避免每条消息都附带音乐卡片。歌曲信息查询失败不影响文字回复。

推荐理由属于当前对话的生成内容，歌曲信息和播放能力则应来自可验证的数据。音乐偏好只使用用户明确表达的内容，暂时的推荐不自动变成长期偏好记忆。

## 背景音乐体验

- **初始静音**：用户点击播放后启动；保存上次选曲与音量，不代表下次打开页面必须自动出声。
- **持续播放**：切换“对话”“知识库”“记忆”等页面时，播放器不销毁、不重新加载歌曲。
- **全局控制**：桌面提供小型常驻播放器；手机端放在底部导航上方，可展开查看曲目和播放列表。输入键盘打开时采用紧凑布局。
- **播放管理**：支持播放、暂停、上一首、下一首、音量、静音、单曲循环和列表循环。
- **播放协调**：应用内播放推荐歌曲时，暂停原背景音乐；结束后只有在用户仍希望播放、且未手动暂停或切换时才恢复。跳转外部音乐 App 时，不假定能控制或检测对方的播放状态。
- **AI 的控制边界**：默认由 AI 提议、用户点击应用。若以后加入“允许 AI 切换背景音乐”，应作为单独的显式设置，不从普通聊天自动推导授权。
- **移动端预期**：可保持当前网页内切换页面时播放，但不承诺手机锁屏、系统挂起或关闭浏览器后仍连续播放。

浏览器可能拒绝未经用户操作的声音播放。实现时需要等待 `play()` 的结果，用真实播放事件更新按钮；遇到权限拒绝时保留可点击的播放入口，而不是把界面直接设成“正在播放”。参见 [MDN 自动播放说明](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)。

## 与表情包共用的消息附件设计

聊天消息保留原有文字正文，附件分别表示图片表情包和歌曲推荐，避免把模型生成的字符串直接当成网页或播放器指令。例如，下方只是应用返回结构的设计示意：

```json
{
  "content": "这首歌的节奏很轻，适合你刚才说的安静阅读。",
  "attachments": [
    {
      "type": "song",
      "catalogId": "应用核实后的歌曲标识",
      "reason": "节奏舒缓，适合阅读",
      "source": "已配置的音乐来源"
    }
  ]
}
```

`catalogId` 由应用核实后产生；具体歌名、歌手、封面、平台地址和播放能力由歌曲目录解析。背景音乐的播放状态保存在播放器中，与聊天记录分开，不因重新绘制聊天消息而改变。

对话中可以同时出现文字、表情包和歌曲卡片，但是否出现各类附件由场景决定，不要求每轮都使用全部类型。

## 对现有项目的具体影响

- **`public/app.js` / `public/index.html`**：现有页面通过 `main.innerHTML` 重新绘制。音频元素和播放器生命周期需要放在 `#main` 之外，消息卡片只向全局播放器发出操作，避免聊天刷新或切换页面中断音乐。
- **`lib/service.mjs`**：将音乐推荐意图与正常回复分开解析；候选校验、歌曲查询、失败回退复用媒体附件的处理流程，不额外发送完整会话给音乐服务。
- **`lib/store.mjs`**：增加歌曲目录、本地音源元数据、播放偏好和消息附件，并迁移旧数据库。外部带时效的播放地址不能当作永久歌曲标识保存。
- **`server.mjs`**：增加受控的本地音频资源路由，支持浏览器拖动进度所需的范围请求。音频文件不应作为大段 Base64 写进消息或 SQLite；目前 JSON 请求上限为 12 MiB，音频上传需单独设计有大小限制的路径。
- **资源策略**：当前 CSP 没有单独的 `media-src`，并且 `connect-src` 只有本域。按选定来源精确开放音频、封面和请求域名，不直接放开任意网址，也不通过通用代理获取模型输出的 URL。
- **`public/styles.css`**：歌曲卡片和全局播放器需要与现有手机底部导航、安全区域、输入键盘和通知位置协调，确保不遮挡发送按钮。

## 验证重点

- 初次进入和刷新页面不突然出声；浏览器拒绝播放时，按钮状态与实际状态一致。
- 发消息、刷新本地数据和切换六个页面不会中断或重复创建播放器。
- 同一时刻不会叠播两首由应用控制的歌曲；用户手动暂停后不会被自动恢复逻辑覆盖。
- 本地文件不存在、格式不支持、网络超时、外部链接过期、账号未授权时都有准确状态。
- 同名歌曲、不同版本和未查到的歌曲不会展示为已经核实的精确结果。
- 旧聊天与数据库迁移不丢记录；历史歌曲卡片重新打开时仍对应原来的歌曲。
- 手机小屏、横屏、键盘打开和播放器展开时均不遮挡聊天、导航或弹窗。

## 建议实施顺序

1. **共用消息附件**：先把表情包和歌曲卡片纳入统一结构，完成历史记录迁移与显示。
2. **本地可用的第一版**：本地表情图库、AI 选图、歌曲推荐卡片，以及全局背景播放器；优先复用用户现有音乐服务的本地曲库，不重复建设音频导入和下载模块。
3. **在线适配器**：接入现有音乐服务的 QQ／网易云搜索和音频流；在线表情包来源另行确定。按各自要求配置地址、凭据与账号授权。
4. **进一步体验**：在音源和播放器稳定后，再考虑 AI 可控换曲、主题播放列表或语音回复时自动降低背景音量。

用户已确认表情包采用本地优先、联网补充，并指定现有音乐平台作为音源，服务地址先留空、后续填写；歌曲偏好以及是否允许 AI 自动切换背景音乐尚未指定。本文中的其他默认交互是建议，不将其记为已经确认的偏好。
